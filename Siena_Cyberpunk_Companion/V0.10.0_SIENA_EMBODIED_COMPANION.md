# v0.10.0 — Siena Embodied Companion

v0.10.0 integrates the proven v0.9.1 queue and dynamic NPC lifecycle into one
deterministic system. Backend commands have exactly three origins (`player`,
`system`, `speech`); CET validates the fixed semantic allowlist and owns every
movement/look-at/body transition. No model response can address this API.

## Runtime flow

`existing telemetry -> embodiment policy -> existing bounded NPC queue ->
existing RedHttpClient -> CET state machine -> single Siena entity`

Existing TTS remains unchanged. Its real playback events produce bounded
`speech_start`/`speech_end` metadata. CET pauses movement, applies idempotent
look-at, renders a sanitized 180-character screen-space subtitle, clears it on
completion/failure/cancellation, and restores Follow or Stay. There is one TTS
worker, one audio queue, one WebSocket, and one CET HTTP client path.

States are `disabled`, `unavailable`, `absent`, `spawning`, `idle`, `following`,
`staying`, `returning`, `conversing`, `suspended`, `cleaning_up`, and `error`.
Transitions are logged and mutually exclusive. Vehicle and configured combat
suspension cancel movement and restore the prior safe mode after exit. Siena
never enters a vehicle and has no combat behavior.

## Safe defaults

Presence and auto-spawn are false; auto-follow, vehicle/combat suspension,
voice embodiment, and subtitles are true once presence is deliberately enabled.
Spawn delay is 3 seconds, follow/return/rescue distances are 2.5/12/40 metres.
Rescue is false and CET rejects enabling it until its Siena-only teleport path is
live validated. All settings are bounded at `/api/v1/npc/settings` and exposed in
the diagnostic panel.

## Player UX and limitations

CET hotkeys cover Toggle Presence, Follow, Stay, Come Here, Talk/Focus, Dismiss,
and status. Talk/Focus safely looks at the player. This repository contains no
confirmed CET-callable microphone/STT entry point, so v0.10.0 does not pretend to
start voice capture and does not add a second STT implementation.

The stable `Siena.SienaCompanion` TweakXL record inherits safe non-quest gameplay
defaults but its production `entityTemplatePath` is
`siena\entities\siena_default.ent` and its appearance is `siena_default`. The real
CR2W `.ent/.app` resources and built archive remain WolvenKit authoring blockers;
guarded deployment refuses to install without them.

The confirmed Stage A source pair is
`ep1\characters\entities\citizen\citizen__ep1_rich_wa.ent` and
`base\characters\appearances\citizen\citizen__rich_wa.app`; the exact source
entity entry display is `citizen__rich_wa_rich_23_casual`, while its actual
`appearanceName` and `.app` definition are `rich_23_casual`. The prepared WolvenKit WScript creates
only Siena-owned copies at `siena\entities\siena_default.ent` and
`siena\appearances\siena_default.app`, retaining unchanged dependencies. It has
not been executed. The exact manual fallback is documented in
`wolvenkit/siena_npc/WOLVENKIT_STANDALONE_AUTHORING.md`.

Current visual/runtime limitations remain explicit: Stage A may look identical to
the existing female citizen even though the `.ent/.app` are Siena-owned copies;
this is not the final custom model. Siena head, hair, body and clothing require a
later Blender pass. Rescue remains disabled. Talk remains focus/look-at unless a
confirmed existing STT entry point is found, and no second STT system may be added.

## Live acceptance — not yet executed

Neither stage below may be marked passed without launching the game and preserving
the CET/TweakXL/ArchiveXL logs.

### Stage A — asset validation

1. Start with the guarded deployment and safe auto-spawn default off.
2. Load a save and confirm no TweakXL, ArchiveXL, RED4ext or redscript errors.
3. Manually Spawn Siena and record controller status/log evidence.
4. Confirm runtime class `NPCPuppet`, record `Siena.SienaCompanion`, current
   appearance `siena_default`, managed/spawned/resolved true and exactly one tag.
5. Confirm neutral/non-hostile behavior and no weapon/combat action.
6. Despawn, return to main menu, and confirm deterministic entity/look-at/movement
   cleanup before proceeding to Stage B.

### Stage B — full embodied companion

1. Enable presence and auto-spawn; confirm one delayed spawn and auto-follow.
2. Walk streets/stairs, then test Stay and Come Here without command spam.
3. Trigger a normal existing Siena conversation/TTS response. Confirm settling,
   look-at, bounded subtitle, real playback, speech cleanup and previous movement
   restoration.
4. Enter/exit a vehicle and start/end combat. Confirm suspension/restoration and
   no attack, weapon or targeting behavior.
5. Stop/restore backend. Confirm bounded cleanup, no crash or arbitrary behavior,
   and recovery through the same transport.
6. Reload the save, return to main menu, and close the game. Confirm one new entity
   per session and no persisted/orphan Siena after every teardown.

No installation or game launch is part of repository validation.

Guarded operator commands are `deploy_siena_embodied_companion.ps1`,
`verify_siena_embodied_companion.ps1`, and
`uninstall_siena_embodied_companion.ps1`. Deployment consumes only a prebuilt
WolvenKit archive and never launches/builds WolvenKit. Verification requires the backend to
be running with `SIENA_CP_NPC_CONTROLLER_ENABLED=true`; it checks v0.10.0 hashes,
the stable TweakXL record, exactly one active Siena CET folder, and safe defaults.
Before deployment, `validate_siena_wolvenkit_assets.ps1` checks the confirmed
source hashes, real CR2W headers, exact record/resource paths, definition
uniqueness, controller boundary, target presence, and detected packed archive.
WolvenKit **File Validation** and **Pack Project** remain explicit GUI actions;
repository validation never marks them complete automatically. Deployment backs
up Siena-owned active paths under repository `.deployment_backups`, verifies
runtime dependency files and hashes, and restores prior Siena paths if copying
fails. The uninstall script can replay that manifest for later rollback.

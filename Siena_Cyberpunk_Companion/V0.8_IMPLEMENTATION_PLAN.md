# v0.8 implementation plan after the audit

This plan starts only after manual research logs are reviewed. It does not authorize implementing all Deep Game State fields at once.

**Update 2026-07-16**: a second evidence pass (direct string extraction from `r6/cache/final.redscripts`/`tweakdb.bin`, plus a real runtime failure log from the installed GameEntityExaminerTool mod) significantly changed the priority order below — see `DEEP_GAME_STATE_CAPABILITIES.md` for full detail. Two changes matter most for planning: (1) `GetComponentClosestToCrosshair(player, nil)` is now **confirmed broken** on this exact build via a real log, not just "unconfirmed" — any crosshair-target design must resolve the `gameTargetSearchQuery` third argument before Gate 2 can use it; (2) RAM/Memory, cyberdeck program slots, wanted level, phone-call state, and item iconic/tag classification now have much stronger, specifically-named candidates and should be the FIRST things run through Gate 1's live probes, ahead of the previously-listed generic list.

## Gate 1: collect runtime evidence

1. Install the isolated research mod without changing `siena_cyberpunk_observer`.
2. Run each manual probe in the matching game state and archive only sanitized method/type results.
3. Promote a capability from candidate to confirmed only when its exact type, nil behavior, cost and session behavior are observed on game `3.0.80.51928`.
4. Keep unsupported capabilities explicit; never substitute UI heuristics for authoritative state.
5. **Priority order for this pass** (highest-confidence new candidates first, since they're most likely to convert to confirmed quickly): `gamedataStatPoolType.Memory` current/max (probe_stat_pools), the 8 `AttachmentSlots.CyberdeckProgram1..8` slots (probe_quickhacks), `Game.GetPreventionSystem()` existence + its returned type's available methods (probe_target), `RPGManager.IsItemIconic`/`gameItemData:HasTag(...)` tried directly from CET Lua for the first time (currently only confirmed from REDscript source — same-name native RTTI functions are usually but not always Lua-reachable), and `StatPoolsSystem:IsStatPoolValid(entity, gamedataStatPoolType.PhoneCallDuration)` as a phone-call-state check.
6. Do not re-attempt `GetComponentClosestToCrosshair` with a 3rd argument until a real `gameTargetSearchQuery` construction path is found in redscript source or NativeDB — guessing a constructor call is exactly the kind of invented method this audit forbids.

## Gate 2: first production slice

Implement only low-cost, high-reliability fields already confirmed through CET:

- progression level/street cred after runtime confirmation;
- targeted money and crafting-component quantities;
- active/right/left weapon identity and static TweakDB metadata;
- bounded applied status-effect IDs;
- mounted vehicle ID;
- lifecycle/loading signal composed from player availability and pre-game state.

Use a versioned additive state model, change detection, session resets and conservative polling. Do not alter mandatory v0.2 fields.

## Gate 3: typed REDscript adapter

Design one read-only REDscript event adapter for fields that plain CET cannot expose reliably: development/perks/skills, cyberware/deck/program slots, weapon ammo, journal tracking and authoritative state-machine transitions. The adapter should emit bounded typed snapshots/events to CET memory only; the existing telemetry client remains the sole backend transport.

`RegisterStatPoolListener`/`UnregisterStatPoolListener` (confirmed real methods, `final.redscripts`) and `RegisterWantedLevelListener`/`UnregisterWantedLevelListener` plus `OnCurrentWantedLevelChanged` (confirmed real event) are the two strongest candidates found so far for genuinely event-driven (non-polling) fields — prioritize confirming their exact registration signature here over building a polling-based Health/RAM/Wanted observer.

## Gate 4: context-sensitive systems

Quickhack cost/availability/trace, stealth/detection, nearby hostiles and wanted state require dedicated evidence and performance measurement. Prefer engine events/listeners. Reject any design that scans world entities, builds all actions, or enumerates inventory/TweakDB every frame.

`GetStealthAwarenessState` and `DetectionPercentage` (both confirmed real symbols, owning class unconfirmed) are the first things to resolve here — if either turns out to be a plain getter on an already-reachable object (e.g. the player puppet or TargetingSystem), stealth/detection could be much cheaper than originally assumed. The crosshair-target break (`gameTargetSearchQuery`) must be resolved before "hacks available on target"/enemy-netrunner classification can even be attempted, since they all depend on a working current-target getter.

## Validation before each promotion

- fake/unit tests for schema/session/change detection;
- Lua/REDscript static checks;
- simulator compatibility and all v0.2-v0.7 regressions;
- live nil/load/death/session-change checks;
- measured polling cost and FPS;
- feature flag rollback with old fields unchanged.

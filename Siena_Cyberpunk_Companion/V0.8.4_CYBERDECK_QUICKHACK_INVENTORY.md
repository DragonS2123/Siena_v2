# v0.8.4 — Cyberdeck & Quickhack Inventory

v0.8.4 is a narrow, read-only production telemetry slice built only from the v0.8.3 calls confirmed in the user's live Cyberpunk 2077 `3.0.80.51928` / CET `1.37.1` log. It adds no target query, inventory scan, game write, HTTP client, transport, WebSocket, event or automatic Siena reaction.

## Live-confirmed runtime paths

Cyberdeck discovery uses both confirmed paths and deduplicates their result by stable TweakDB record ID:

1. `EquipmentSystem.GetData(player):GetActiveItem(gamedataEquipmentArea.SystemReplacementCW)`.
2. `Game.GetScriptableSystemsContainer():Get("EquipmentSystem").GetItemsInArea(player, gamedataEquipmentArea.SystemReplacementCW)`.
3. `Game.GetTransactionSystem():GetItemData(player, itemID)`.
4. Stable identity is `itemID.id`; userdata pointers and ItemID RNG fields are never serialized.

The live log returned `Items.AdvancedNetwatchNetdriverMKLegendary` through both discovery paths. Production keeps one candidate because the stable record IDs match.

`SystemReplacementCW` also contains Sandevistan and Berserk operating systems. An item is accepted only when item data exists, `itemID.id` is stable and `gameItemData:HasTag(CName.new("Cyberdeck"))` returns true. `Cyberware` alone never classifies an item as a cyberdeck.

Metadata uses only:

- `gameItemData:GetItemType()`;
- `RPGManager.GetItemDataQuality(gameItemData)`;
- `RPGManager.IsItemDataIconic(gameItemData)`;
- `TweakDBInterface.GetItemRecord(recordID)` and bounded `record:Tags()`;
- direct allowlisted tag checks for `Cyberdeck`, `Cyberware` and `Iconic_OS_CW`.

## Installed programs

Programs are read from the equipped deck only:

- `cyberdeckItemData:GetItemParts()`;
- `InnerItemData.GetSlotID(part)`;
- `InnerItemData.GetItemID(part)` and `programItemID.id`;
- `RPGManager.GetInnerItemDataQuality(part)`;
- `RPGManager.IsInnerItemDataIconic(part)`.

Only exact slot IDs `AttachmentSlots.CyberdeckProgram1` through `AttachmentSlots.CyberdeckProgram8` are accepted. The live `AttachmentSlots.GenericItemRoot` / `Items.GenericItemRoot` part is excluded. Programs are deduplicated by `(stable slot ID, stable program record ID)` and sorted by numeric slot order. `TransactionSystem:GetItemData(player, programItemID)` is not used because the live runtime returned nil for installed programs.

All collections use the existing configured collection bound. The serialized program list is additionally capped at the eight confirmed program slots and exposes `truncated` when output is cut. No raw tables, userdata, hash values or RNG seeds cross the bridge.

## Capacity

Capacity is derived only from:

- `cyberdeckItemData:GetUsedSlotsOnItem()`;
- `cyberdeckItemData:GetEmptySlotsOnItem()`.

Both lists are bounded and filtered to the eight exact program slot IDs. `used` and `empty` are unique filtered counts. `total` is the union of the stable used and empty slot IDs; it is not hardcoded to eight. `GenericItemRoot` never contributes.

If either collection is unavailable, its count is null and total is null. If the same stable slot occurs in both collections, all capacity counts are null while the independently confirmed program list remains available.

## Polling, caching and capabilities

Cyberdeck state polls at a default interval of 2000 ms, separately from the 250 ms health/RAM telemetry sample. The cache contains only safe serialized values. It is cleared together with all session-dependent caches when the player disappears.

The bridge exposes default-false capability flags:

- `cyberdeck_identity` after a successful equipment-area/active-item read;
- `cyberdeck_metadata` after successful item type, quality, iconic and bounded record-tag reads;
- `cyberdeck_programs` after a successful bounded `GetItemParts` read;
- `cyberdeck_capacity` only after both slot collections are successfully read and consistent.

Unsupported action metadata is never marked available.

## Nullable wire and SceneContext behavior

`deep_game_state.cyberdeck` is optional and nullable. No player, no operating-system item, a non-cyberdeck OS, or an older payload is represented without errors. Runtime-dependent subfields remain nullable. Backend lists are strictly bounded and accept stable `Items.*`/confirmed slot strings only.

SceneContext adds nullable deck ID, quality, iconic state, program count and capacity plus at most eight installed quickhack record IDs. State observation updates context only; it creates no quickhack loadout event or reaction.

The existing frontend Deep Game State card shows shortened deck/program record IDs, iconic marker, quality, used/total capacity and slot numbers. Old payloads render `—`; a successful identity read with no cyberdeck renders `No cyberdeck`.

## Explicitly unsupported

v0.8.4 does not expose actual/base RAM cost, upload time, duration, cooldown, spread, trace, execution/queue state, target availability, target/enemy/nearby scans, general cyberware or inventory enumeration, quests, perks or localized names.

Runtime-proven unavailable globals `GetSlotsForCyberdeckFromItemData` and `GetPlayerQuickHackInCyberDeck` are forbidden in production and are not called.

## Manual live smoke

1. Install the v0.8.4 production observer and start the existing backend/frontend stack.
2. Load a save with a cyberdeck. Wait at least two seconds and verify one stable deck ID, correct quality/iconic state, ordered program slots and capacity.
3. Confirm active-item and area discovery do not duplicate the deck or programs.
4. Remove/add a quickhack through the normal game UI, wait two seconds and verify only the affected slot/count changes.
5. Equip a different deck and verify stable ID, metadata, programs and capacity refresh.
6. Equip Sandevistan or Berserk and verify `cyberdeck` becomes null and the UI shows `No cyberdeck`.
7. Test an empty deck and a partially filled deck; capacity must come from used/empty slot collections rather than a hardcoded value.
8. Reload the save and verify no old deck/program handle survives the session reset.
9. Return to the main menu and verify nullable/unavailable telemetry without log errors.
10. Confirm the existing WebSocket and RedHttpClient transport counts are unchanged and no loadout reaction is generated.

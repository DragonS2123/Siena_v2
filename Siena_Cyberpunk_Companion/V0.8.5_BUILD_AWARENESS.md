# v0.8.5 Build Awareness

v0.8.5 is a backend-derived, read-only interpretation of telemetry already collected by v0.8.1 through v0.8.4. It does not add a CET runtime call, game-state write, HTTP client, WebSocket, transport, or automatic reaction trigger. The structured profile is deterministic; no LLM participates in classification or scoring.

## Observations and inferences

Observed inputs retain their game-fact meaning: cyberdeck record ID, quality, iconic state, installed quickhack record IDs and slot IDs, capacity, maximum RAM, maximum health, armor, and current weapon record ID. The weapon is context only and never defines the build.

Inferred outputs are explicitly separate: program categories, dominant category, build style, evidence keys, limitations, and confidence. They are nullable or marked unknown when the corresponding observation is unavailable. The prompt describes style only as an observed tendency and forbids invented attributes, perks, program effects, or costs.

`deep_game_state.build_profile` is optional. Old v0.7, v0.8.1, v0.8.2, and v0.8.4 payloads remain valid without it. A profile is not produced when the player entity/session is unavailable or pre-game. Since the service is stateless and derives each packet independently, session unload cannot retain stale equipment.

Every other record ID is `unknown`. Unknown records reduce confidence. No RAM cost, damage, upload time, cooldown, duration, spread, trace, or target behavior is inferred.

## Style rules

- Confirmed absence of a valid deck: `no_cyberdeck`.
- Valid cyberdeck with no catalog-known program: `cyberdeck_unknown`.
- A classified category accounting for at least 60% of catalog-known programs: `offensive_netrunner`, `control_netrunner`, or `recon_netrunner`.
- Otherwise: `mixed_netrunner`.

Utility remains a catalog category but has no broad build style in this slice, so a utility-dominant set is conservatively `mixed_netrunner`. Stealth, tank, gunslinger, blades, sniper, and other character archetypes are unsupported.

## Deterministic confidence

For a valid cyberdeck, confidence starts at `0.25`, then adds:

- `0.15` for consistent installed/capacity counts;
- `0.10` when the bounded program list is available;
- up to `0.30` multiplied by `catalog-known / installed`;
- `0.10` when maximum RAM is available;
- `0.10` for unique, consistent program slot IDs.

It subtracts `0.15` for a truncated list and `0.15` when the reported used count disagrees with installed programs. Missing capacity simply earns no capacity points. The result is rounded to two decimals and clamped to `0.0-1.0`. Confirmed no-cyberdeck has `0.80`; absence without the identity capability has `0.35` plus an explicit limitation.

Evidence and limitations are bounded to 12 entries. SceneContext projects only bounded counts, evidence, and limitations. Profile changes update context but do not synthesize a game event, reaction opportunity, or voice request.

## Unsupported dimensions

Attributes, perks, skill trees, full cyberware, full weapon inventory, weapon archetypes, detailed damage statistics, nearby entities, targets, quests, and quickhack action metadata are unavailable. The active weapon cannot establish a complete character build.

## Example

Eight installed programs with five exact offensive mappings, one control mapping, one recon mapping, and unknown `CommsCallIn` produce an `offensive_netrunner` tendency. The profile reports seven known records, one unknown record, its deterministic confidence, the supporting count keys, and the unavailable build dimensions.

## Live smoke procedure

1. Start the existing backend, frontend, and the single CET observer transport.
2. Load a save and verify `deep_game_state.build_profile.profile_version` is `0.8.5` on `/api/v1/telemetry/latest` and the existing WebSocket state envelope.
3. Draw and holster a weapon; confirm only `current_weapon_record_id` context changes and style does not become a weapon archetype.
4. Inspect the Build Awareness section for style, confidence, dominant category, known/unknown counts, bounded evidence, and limitations.
5. Holster/unload or return to pre-game; confirm unavailable player state yields a null profile and no stale deck remains.
6. Confirm no reaction or voice is produced solely by a build-profile/loadout change. A pre-existing meaningful event may include one relevant observed-tendency fact in its prompt context.

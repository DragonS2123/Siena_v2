# v0.9.0 Contextual Companion Intelligence

## Architecture

`ContextualCompanion` is a deterministic, session-scoped layer between the existing `CompanionBehaviorPolicy` candidate generation and `ReactionDispatchService`. It consumes only normalized meaningful events and bounded SceneContext fields. It never reads raw telemetry samples, calls Cyberpunk, controls the game, or invokes an LLM to decide whether Siena may react.

The path is:

1. CET or simulator state enters the existing telemetry endpoint.
2. Existing diff, synthesis, filtering, and SceneContext logic produce meaningful events.
3. Existing policy proposes a reaction opportunity.
4. Contextual arbitration groups, suppresses, promotes, or decorates that opportunity.
5. Only an allowed opportunity reaches the existing template/Siena Core provider and existing voice/presence pipeline.

Setting `contextual_companion_enabled=false` returns the legacy v0.8.5 opportunity unchanged.

## Deterministic state rules

The diagnostic situation is inferred, never presented as a direct game fact:

- `unavailable`: player or session is explicitly unavailable;
- `loading`: pre-game or a newly reset session without confirmed ready state;
- `danger`: critical health, including health at or below 10%;
- `recovery`: recovery phase/trend or a recovery event within the bounded 15-second continuity window;
- `combat`: confirmed existing combat state;
- `driving`: confirmed mounted/vehicle state outside the higher-priority states;
- `idle`: existing idle phase;
- `exploration`: ready session outside the states above.

Old payloads that lack deep availability fields remain compatible and use the previous event behavior.

## Event window and short-term memory

Only normalized meaningful events enter the session window. Defaults are 20 items and 60 seconds. Entries contain event ID, stable event type, timestamp, priority, optional sequence, and whether a reaction was emitted. Event IDs are deduplicated and ordering follows event timestamps. No prompt, full model response, userdata, hidden reasoning, or raw sample is retained.

Pending low-priority grouping is separately bounded to three candidates. Session change, explicit player/session unload, or session end clears events, pending candidates, recent category, equipment context, and recovery memory. Nothing is written to Siena long-term memory.

## Grouping and arbitration

The default grouping window is three seconds and is configurable from 0.25 to 5 seconds.

- Health-low and RAM-low candidates wait briefly for escalation.
- Critical health is immediate and promotes/removes a pending lower health warning.
- RAM exhausted may promote a pending RAM-low warning and is reaction-eligible only in combat.
- Recent critical-health and RAM-exhausted types can coexist in one compact tactical context.
- Weapon changes and unnamed status-effect count changes are context-only/suppressed before they consume reaction cooldown.
- Critical candidates retain the existing ability to replace weaker queued reaction requests.
- Profile changes are state context only and never create synthesized events or reaction candidates.

Existing repetition, scene-budget, provider cooldown, stale-request, priority queue, voice queue, and session guards remain active. The LLM receives no route around suppression because it is called only after deterministic arbitration accepts an opportunity.

## Tactical and build context

The provider receives one primary event, at most eight related/recent event types, current situation, combat/driving flags, health and RAM states/percentages, active weapon record ID, bounded deck/program context, recovery marker, urgency, and at most eight limitations. The complete telemetry payload is never sent.

Build Awareness is supporting evidence only. A build profile below 0.60 confidence is omitted and adds `build_profile_low_confidence`. `no_cyberdeck` remains explicit so the model must not suggest installed quickhacks. The prompt prohibits invented RAM costs, cooldowns, perks, cyberware bonuses, unseen enemies, targets, and exact damage causes. It asks for one short Russian reaction and at most one relevant build fact.

The repeated-category marker lets the model vary wording after a recent health/RAM situation without storing full responses or reasoning.

## Voice policy

- Critical and high warning opportunities use `voice_and_text` through the existing bounded voice/TTS path.
- Recovery defaults to `text_only`; `recovery_voice_enabled=true` permits existing voice policy to consider it.
- Medium/low contextual, weapon, build, and status-effect information is text-only or suppressed.
- `text_only` is enforced before TTS queueing. No second worker, audio queue, or interruption mechanism is added.

## Configuration

| Setting | Default | Validation |
| --- | ---: | --- |
| `contextual_companion_enabled` | `true` | boolean |
| `context_event_window_seconds` | `60` | `>0`, at most `600` |
| `context_event_window_max_items` | `20` | `1..100` |
| `grouping_window_seconds` | `3` | `0.25..5` |
| `low_priority_queue_limit` | `3` | `1..10` |
| `recovery_voice_enabled` | `false` | boolean |
| `build_aware_reactions_enabled` | `true` | boolean |

Environment variables use the existing `SIENA_CP_` prefix.

## Explainability and diagnostics

The existing WebSocket carries optional `contextual_companion_status` and `contextual_companion_trace` envelopes. Trace types include state change, candidate creation/grouping, suppression, promotion, replacement, and emission with compact reason keys. Hidden model reasoning is never logged.

The frontend Contextual Companion card shows situation, urgency, pending primary event, grouped types, bounded queue size, last emitted category, latest suppression reason, and event-window size. It is diagnostics only, not chat or control UI.

## Limitations

The system cannot see targets, nearby enemies, enemy type, enemy netrunners, exact damage cause, quests, dialogue choices, perks, attributes, full cyberware, full inventory, or quickhack action metadata. It cannot move, switch weapons, execute quickhacks, automate combat, or write game state.

## Live smoke procedure

1. Start the existing backend/frontend and the single CET observer.
2. Load a save and confirm the Contextual Companion card changes from loading to exploration, driving, combat, or danger using existing telemetry.
3. Trigger health low followed quickly by critical; confirm the low candidate groups and one immediate critical reaction is emitted.
4. Exhaust RAM during combat; confirm RAM/build context is compact, and repeat outside combat to confirm suppression.
5. Change/draw a weapon during combat; confirm it appears as context but does not speak by itself.
6. Recover after danger; confirm recovery is text-only unless `recovery_voice_enabled` is enabled.
7. Unload the player or change sessions; confirm event window, pending queue, category memory, and equipment context reset.
8. Disable `contextual_companion_enabled`; confirm the v0.8.5 reaction path remains operational.
9. Verify no reaction is emitted solely because `build_profile` changed.

# v0.9.1 — Siena NPC Presence Controller

## Outcome and boundary

v0.9.1 introduces a disabled-by-default deterministic production controller for one physical Siena shell. It does not implement Siena's final appearance, autonomous behavior, animation, TTS synchronization, combat, quests, vehicles, persistence, or LLM-issued commands.

The implementation is split into three explicit layers:

1. The existing frontend submits a manual enum command to the local backend.
2. A bounded backend queue validates, expires, coalesces, prioritizes, and one-time claims commands.
3. An isolated CET controller maps the fixed allowlist to locally compiled, live-confirmed game calls.

No record, template, position, EntityID, class, game method name, or arbitrary parameter crosses the HTTP boundary. The reaction, contextual-companion, Siena Core, scheduler, and TTS services do not reference the NPC queue.

## Live-confirmed foundation

The user's completed v0.9.0/v0.9.0.1 runtime gates confirmed on the installed game build:

- DynamicEntitySystem availability, readiness and restoration;
- `DynamicEntitySpec` and the fixed `Character.CitizenRichFemaleCasual` record;
- creation, tag duplicate guard, direct returned EntityID, resolution as `NPCPuppet`, alive state, AI controller and ReactionManager;
- non-teleport native Follow, movement cancellation for Stay, native Come Here with navigation enabled;
- temporary look-at and clear look-at;
- PlayerPuppet detach cleanup;
- no redscript bridge requirement for this slice.

The production controller adds no game-runtime API beyond those researched and live-tested calls.

## Temporary body

`Character.CitizenRichFemaleCasual` is hard-coded game-side and is visibly labelled temporary in the UI. It is not accepted from backend input. It is a generic female citizen shell, not a female-V standalone asset and not Siena's final appearance.

The spec always uses `persistState=false`, `persistSpawn=false`, `alwaysSpawned=false`, `active=true`, a stable `SienaNpcProduction` tag, a two-metre forward offset, 0.10-metre vertical offset, and the player's existing world orientation. One tagged entity is the maximum.

Spawn validation is bounded to three seconds. A resolved entity must be managed, spawned, alive, `NPCPuppet`, and expose both AI controller and ReactionManager. Failure deletes the owned tagged entity, clears references and reports `spawn_failed_validation`.

## Command protocol

Only these values exist: `spawn`, `despawn`, `follow`, `stay`, `come_here`, `look_at_player`, `clear_look_at`, and `status`.

Routes:

- `POST /api/v1/npc/commands` with exactly `{ "command": "<enum>" }`;
- `GET /api/v1/npc/commands/next` for one-time CET claim;
- `POST /api/v1/npc/commands/{id}/result` for bounded result/status acknowledgement;
- `GET /api/v1/npc/status` for the diagnostic card.

The queue maximum defaults to 16. Movement/gaze commands expire after 10 seconds, spawn/despawn after 30 seconds, and status after 5 seconds. Duplicate queued Follow commands coalesce. Despawn removes queued lower-priority work and is placed first. Expired work is discarded. Claimed IDs and status contain no runtime userdata.

The CET client uses the already installed `AsyncHttpClient`/RedHttpClient API and the existing loopback backend URL. It maintains one outstanding request, validates the response allowlist and numeric expiry locally, polls every 400 ms only with a valid player session, and applies exponential backoff up to ten seconds. Backend loss never despawns the NPC; session loss does.

## Idempotence and cleanup

- Follow is not resubmitted when the same controller is already following.
- Stay cancels at most one movement command and succeeds harmlessly without one.
- Come Here cancels prior movement and submits one native navigation command with `ignoreNavigation=false`.
- Look At does not resubmit while active; Clear Look At is harmless when inactive.
- Despawn cancels movement, clears gaze, deletes only the owned/tagged ID, and tolerates absence.
- Player detach, pre-game/main-menu transition, player loss after an active session, DynamicEntitySystem loss, CET shutdown and mod reload clear commands and references. The controller never automatically restores or respawns.

## Configuration

Backend settings are validated under the existing `SIENA_CP_` prefix:

- `NPC_CONTROLLER_ENABLED=false`
- `NPC_COMMAND_POLL_INTERVAL_MS=400` (250–500)
- `NPC_COMMAND_QUEUE_MAX=16`
- `NPC_SPAWN_DISTANCE=2.0` (1.5–2.5)
- `NPC_VERTICAL_OFFSET=0.1`
- `NPC_COMMAND_EXPIRY_SECONDS=10`
- `NPC_AUTO_SPAWN=false` — typed as literal false

Both backend and installed CET `config.lua` must be explicitly enabled by the operator. Auto-spawn remains false and is not a frontend control.

## Installation and live smoke

With Cyberpunk closed:

```powershell
.\scripts\install_siena_npc_controller.ps1 -GamePath 'B:\SteamLibrary\steamapps\common\Cyberpunk 2077'
.\scripts\verify_siena_npc_controller.ps1 -GamePath 'B:\SteamLibrary\steamapps\common\Cyberpunk 2077'
```

Set `SIENA_CP_NPC_CONTROLLER_ENABLED=true`, set only the installed controller's `enabled=true`, and leave `npc_auto_spawn=false`. Start backend, frontend and game manually.

Smoke order: Refresh Status, Spawn, wait for resolved `NPCPuppet`, Spawn twice, Follow twice, Stay twice, Come Here, Look At twice, Clear Look At twice, Despawn twice. Then repeat cleanup tests for main menu, same-save reload, another-save load, CET Reload All Mods, normal exit and unload while following. Require one shell maximum, no teleport/combat/weapon/quest activity, no persistence and no stale command.

This coding pass does not install or launch the game and therefore does not claim v0.9.1 live-smoke success.

Uninstall with the game closed:

```powershell
.\scripts\uninstall_siena_npc_controller.ps1 -GamePath 'B:\SteamLibrary\steamapps\common\Cyberpunk 2077' -Confirm:$false
```

Backups are outside active CET mods under `<game root>\siena_npc_controller_backups`.

## Static and automated validation

The implementation is covered by backend queue/API tests for allowlist validation, capacity, expiry, one-time claim, acknowledgement, Follow coalescing, Despawn priority, nullable status, disabled behavior and old API compatibility. Frontend tests cover the exact button allowlist, loading/disabled behavior, error selection, nullable rendering and the temporary-body warning.

The controller checker parses every production-controller Lua file and rejects automatic spawn, persistence, arbitrary dispatch, game identifiers from HTTP, player/inventory/quest/TweakDB/combat/teleport/world-scan writes, another transport dependency, a second frontend WebSocket, or NPC queue access from Siena Core/reaction services. Production observer, research harnesses, PowerShell syntax, frontend build and the complete backend suite are part of the release validation.

Final coding-pass results: 294 backend tests passed; 46 frontend tests passed; the frontend production build passed; production Lua (11 files), Deep Game State research Lua (5), NPC research Lua (5), and NPC controller Lua (6) passed their static checks; all PowerShell scripts parsed; and `git diff --check` passed. The audit found exactly one frontend WebSocket constructor, zero new HTTP/socket dependencies, and zero NPC-queue references in the LLM/reaction services. The existing production observer aggregate hash remained `15EB7B45B4B3E6E218B0B6554FB99B3E0304EF29027BDCCAC1DF9BD68D425F48`.

## Final-appearance blockers and next steps

The remaining body work is a standalone female-V-derived NPC-compatible asset with recorded appearance parameters, later extended by Siena's Blender model. That requires its own WolvenKit/ArchiveXL asset research and must not introduce runtime TweakDB cloning. Animation/workspots, lip-sync and voice/body timing remain separate future gates.
